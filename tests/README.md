# Тестирование Chef frontend

Актуализировано по исходникам **27.11.2026**. Это единая точка входа для существующих тестов репозитория `jacochef-next`: что они проверяют, какое окружение используют и как их запускать. Наличие теста в списке не означает, что он успешно проходит сейчас; результаты конкретного запуска нужно фиксировать отдельно.

## Планы сценариев первых модулей

| Модуль          | Список сценариев                               |
| --------------- | ---------------------------------------------- |
| Накладные       | [tests/plans/billing.md](plans/billing.md)     |
| Управление кафе | [tests/plans/cafe-edit.md](plans/cafe-edit.md) |

Это план последовательного добавления unit/компонентных тестов. **P0** — первая очередь: основные операции и ограничения, **P1** — следующие варианты и регрессии. **Запланировано** — сценарий ещё предстоит автоматизировать; **Частично** — существующие тесты проверяют только указанную часть; **Покрыто** — есть конкретные тесты на весь описанный сценарий и подтверждённый успешный запуск. При изменении статуса указывайте соответствующие файлы и границы проверки. Сам список сценариев не подтверждает готовое покрытие или работу настоящего API.

На дату сверки: **50 прежних файлов `*.test.mjs` в 9 unit-группах**, **12 файлов Vitest** и **9 файлов `*.spec.js` в 3 браузерных группах**. Число файлов не равно числу тестов: есть циклы, параметризация и два браузерных проекта склада. Перечень Playwright без выполнения обнаружил 22 теста дизайн-системы и 116 запусков склада (58 сценариев × 2 проекта); общий конфиг обнаружил 86 тестов, включая 6 smoke-проверок графика.

**Vitest и React Testing Library подключены отдельно от прежнего набора.** Файлы `tests/unit` продолжают запускаться через `node:test`. Семь хрупких проверок текста графика персонала заменены поведенческими тестами Vitest; остальные прежние проверки сохранены. Не все прежние проверки являются юнит-тестами поведения:

- **Функциональные** вызывают функцию, модель или store и проверяют результат.
- **Изолированные обработчики** выполняют код с подменёнными API, браузерным окружением и React-хуками; часть исходника загружается через `vm` или преобразуется Babel.
- **Проверки исходников** ищут текст, регулярные выражения или узлы AST. Они фиксируют способ реализации, но сами не подтверждают поведение компонента или его вид в браузере.

## С чего запускать

Все команды выполняются из корня `jacochef-next`. Для unit-тестов не нужны запущенные фронт, Docker или Laravel. Проверено на Node.js **24.13.1 / npm 11.8.0**; для ветки Node 22 нужен **22.13.0 или новее**. Новый unit CI использует Node.js **24.13.1**, прежние проверки публикации — Node 22. Если зависимостей нет, установить их по `package-lock.json` командой `npm ci`.

```bash
# Прежние Node unit-тесты и новые Vitest-тесты
npm run test:unit

# Только прежние тесты / только Vitest
npm run test:legacy
npm run test:vitest

# Отдельная группа (объединённый запуск выбирает только существующие наборы)
npm run test:unit -- --scope=staff-schedule
npm run test:unit -- --scope=auth
npm run test:unit -- --scope=infrastructure

# Наблюдение за изменениями / отчёт покрытия новых тестов
npm run test:vitest:watch
npm run test:vitest:coverage

# Только чистая логика / только React-компоненты Vitest
npm run test:vitest -- --project=unit
npm run test:vitest -- --project=components

# Один прежний файл или отбор по имени
node --test tests/unit/staff-schedule/payroll.test.mjs
node --test --test-name-pattern='computeTotalSum' tests/unit/staff-schedule/payroll.test.mjs
```

**`npm run test:unit` не запускает браузерные E2E-сценарии Шефа.** Оба unit-раннера выполняются даже при ошибке первого; общий код завершения ненулевой, если любой набор упал или не запустился. Исключения CI не добавляются автоматически. Скрипта `npm test` больше нет: используйте явное имя `test:unit`.

## Новое окружение Vitest

Конфигурация находится в [vitest.config.mjs](../vitest.config.mjs). Она включает только `tests/vitest/unit/**/*.test.{js,mjs}` и `tests/vitest/components/**/*.test.{js,jsx,mjs}`. Прежние `tests/unit` и Playwright Vitest не подхватывает. Есть две группы: `unit` с окружением `node` и `components` с `jsdom`; импорт `@/` указывает на корень. JSX внутри существующих `.js` обрабатывается без переименования файлов приложения.

Закреплены версии devDependencies: `vitest@5.1.2`, `vite@8.4.0`, `@vitejs/plugin-react@6.3.0`, `jsdom@29.0.0`, `@testing-library/react@16.3.3`, `@testing-library/dom@10.4.2`, `@testing-library/user-event@14.6.13`, `@testing-library/jest-dom@8.0.0`, `msw@2.15.0`, `@vitest/coverage-v8@5.1.2`. `jsdom` 29 совместим с текущим Node 24.13.1; MSW 2 не требует обновления прежнего транзитивного TypeScript 4.9.5. Версии Vitest и coverage-провайдера совпадают. Vite используется только для тестов; Next.js по-прежнему запускается своей командой.

- [setup.node.js](vitest/setup.node.js) и [setup.dom.js](vitest/setup.dom.js) подключают MSW, проверяют неожиданные запросы и очищают окружение после теста.
- [network.js](vitest/network.js) экспортирует `server`. Ответы задаются в тесте через `server.use(...)` и сбрасываются после него. Необработанный запрос блокируется **и фиксируется как ошибка теста при завершении**, даже если приложение поймало сетевую ошибку. Исключений для настоящего API нет.
- Рабочие `.env` не загружаются. Тестовый API принудительно задан как `http://chef.test/api`, URL jsdom — `http://chef.test/`. Тестам не требуется подключение к боевой или тестовой БД.
- [render.jsx](vitest/render.jsx) предоставляет `renderWithProviders`: настоящая тема MUI и локализация Day.js. [Загрузчик Roboto](vitest/mocks/next-font.js) заменяет `next/font/google` без загрузки шрифта.
- После каждого компонентного теста удаляется DOM, очищаются `localStorage`, `sessionStorage` и cookies, сбрасываются два существующих store кафе. Подмены функций, глобальных значений и env восстанавливаются. `matchMedia` моделирует desktop-режим, `ResizeObserver` — минимальный интерфейс без расчёта геометрии; реальные размеры/вёрстку jsdom не проверяет.
- Карты, OCR, Dropzone и другие внешние функции следует подменять только в тестах соответствующих сценариев. Тестовый helper не заменяет бизнес-компоненты общими заглушками.

Начальные тесты проверяют работоспособность инфраструктуры, **не полное покрытие двух модулей**:

## Как добавлять тесты по плану

1. Выберите сценарий и проверьте его текущую реализацию, поля API и правила доступа. Чистую логику размещайте в `tests/vitest/unit/<module>`, React-компоненты и хуки — в `tests/vitest/components/<module>`, с расширениями файлов из раздела конфигурации выше. Новые module-папки добавляются по мере появления тестов; файлы планов сами не создают запускаемый набор.
2. Проверяйте наблюдаемый результат: состояние/результат функции, действие пользователя, разрешённые и запрещённые операции, payload и обработку ответа. Исполняйте настоящую проверяемую логику; подменяйте внешнюю границу. HTTP-ответы задавайте через общий MSW `server.use(...)`, для изолированных хуков допустима подмена API-адаптера. Настоящий API и БД не используются; неизвестный HTTP должен оставаться ошибкой теста.
3. Для React используйте существующий `renderWithProviders`, когда нужна тема/локализация. Общий setup уже очищает DOM, HTTP handlers и хранилища, восстанавливает подмены; собственные store, таймеры и внешние ресурсы теста также должны возвращаться в исходное состояние. Дату фиксируйте для сценариев, зависящих от периода.
4. Сначала выполните новый файл через `npm run test:vitest -- <путь-к-файлу>`, затем общий `npm run test:unit`. Обновите статус и ссылку в плане по фактически проверенной части. Сейчас `billing` и `cafe-edit` ещё не являются доступными scopes: `--scope` работает только для уже созданных папок с тестами. Начальные проверки этих модулей находятся в `infrastructure`; действующие команды приведены выше.

### График персонала: существующий smoke с настоящим API

**Не запускать против API, подключённого к боевой БД.** Проверка адреса `localhost`/`127.0.0.1` в тестах не проверяет, к какой БД подключён Laravel. Набор вызывает `save_user_day`, `save_user_month`, `save_userPriceH`, `save_dir_lv`, `save_user_give_price`, `save_user_give_cart_price` и `save_user_withheld`, даже когда пытается сохранить прежние значения.

Этот набор требует предварительной сверки с текущим модулем: smoke ожидает применение фильтров только кнопкой «Обновить», а текущий unit-файл проверяет автозагрузку при смене кафе/месяца. Кроме того, подготовка сессии использует старый legacy-token, а не реальный новый вход с bearer-токеном. Применимость текущей авторизации нужно проверять отдельно.

На **отдельном тестовом стенде с тестовой БД**, после подготовки подходящего пользователя, данных графика и совместимой авторизации:

```bash
# В отдельном терминале запустить фронт, если он ещё не запущен
npm run dev

# Запуск существующего smoke-набора
npm run test:e2e -- --scope=staff-schedule

# Сначала только перечень тестов
npm run test:e2e -- --scope=staff-schedule --list
```

[smoke.spec.js](e2e/staff-schedule/smoke.spec.js) содержит проверки bootstrap/графика, старого сценария фильтров, чтения дневной/месячной карточки, запросов сохранения и ответа экспорта журнала здоровья. Утверждение экспорта ограничено наличием `Content-Type`, а не содержимым файла. Для части выплат допускается ответ с бизнес-ошибкой и проверяется наличие payload. Это ограниченный smoke, а не полное подтверждение корректности расчётов и сохранённых данных.

[localEnv.js](e2e/support/localEnv.js) читает `NEXT_PUBLIC_API_URL` из окружения процесса или `.env.development`; запасной API — `http://127.0.0.1:8000/api`. Фронт задаётся через `E2E_BASE_URL`, по умолчанию `http://localhost:3000`. Тестовая идентичность задаётся через `STAFF_SCHEDULE_SMOKE_LOGIN` и `STAFF_SCHEDULE_SMOKE_USER_ID`; значения по умолчанию в helper не являются входом под текущим пользователем браузера. `PLAYWRIGHT_HEADLESS=0` или `--headed` включают видимый браузер в общем конфиге.

## Как устроены команды запуска

[Обёртка](../scripts/test.js) разделяет unit и e2e. Прямой запуск `node scripts/test.js` выбирает только оба unit-набора; внутренний `--type=all` также означает оба unit-раннера, без Playwright.

| Команда / аргумент          | Реальное действие                                                                                       |
| --------------------------- | ------------------------------------------------------------------------------------------------------- |
| `npm run test:unit`         | Выполняет прежний Node-набор и новый Vitest, собирает общий код завершения                              |
| `npm run test:legacy`       | Только `tests/unit/**/*.test.{mjs,js,cjs}` через `node --test`                                          |
| `npm run test:vitest`       | Только Vitest: один прогон; его параметры можно передать после `--`                                     |
| `npm run test:vitest:watch` | Vitest в режиме наблюдения, без прежних Node-тестов                                                     |
| `npm run test:e2e`          | Только Playwright с общим конфигом; для склада и Storybook предпочтительны их отдельные команды         |
| `--scope=<папка>`           | В обёртке выбирает папку модуля; регистр приводится к нижнему, `_` заменяется на `-`                    |
| `--grep=<имя>`              | В обёртке фильтрует имена проверок соответствующего раннера; в объединённом запуске применяется к обоим |
| `--headed`                  | Только Playwright; с `test:unit` завершается понятной ошибкой                                           |
| `--list`, `--project`       | В обёртке разрешены только для отдельного Vitest/e2e; комбинированный unit их отвергает                 |

Прежние unit-scopes: `api`, `auth`, `check-check`, `cleanings`, `employees`, `errors-management`, `site-setting`, `sklad`, `staff-schedule`. У нового набора scopes — `infrastructure` и `staff-schedule`. Объединённая команда выбирает scope из обоих наборов; если он есть только в одном, другой пропускается. Неизвестный scope или параметр вызывает ошибку.

E2E-scopes: `design-system`, `sklad-items`, `staff-schedule`; `support` — вспомогательный код. При явно выбранном scope `design-system` или `sklad-items` обёртка выбирает соответствующий отдельный конфиг. Непереданный scope у `test:e2e` по-прежнему использует общий конфиг и может включить smoke с настоящим API. **Не запускайте его на текущем API с боевой БД.**

Для одного прежнего файла или произвольных параметров Node удобнее прямой `node --test` с параметрами перед путями. Обёртка также передаёт параметры после отдельного `--` выбранному одиночному раннеру; комбинированный запуск отвергает такие неоднозначные параметры. `--type=visual` не поддерживается.

## Отчёты, скриншоты и повторы

`npm run test:unit`, `npm run test:legacy` и `npm run test:e2e` по умолчанию выводят краткий отчёт на русском:

- сколько тестов выполнено, успешно, с ошибкой, пропущено/отменено; у Playwright отдельно отмечается нестабильность после повтора;
- для каждого неуспешного теста — точное имя, относительный файл/строка и короткая причина;
- ошибки подготовки/запуска показываются отдельно и сохраняют ненулевой код завершения, даже если ни один тест не начался;
- большой фактический текст исходника, diff, stack trace и сообщения тестов не печатаются в терминал; они сохраняются в подробных файлах.

Новый запуск создаёт отдельную папку `test-reports/summary/run-*`. Она отделена от `test-results`, который Playwright очищает перед запуском; журналы не удаляются вместе с браузерными артефактами. `test-reports` исключён из Git и Docker-контекста. В ней находятся `summary.json`, отчёты отдельных раннеров и `*-full.log`. Node формирует данные из событий `node:test`, Vitest — из JSON-репортёра, Playwright — из собственных событий; количества не вычисляются из строк терминала. Если раннер не смог создать отчёт, команда сообщает об этом как об ошибке запуска и указывает папку с доступными подробностями. Утрата журнала отмечается отдельной ошибкой; наличие полного вывода в таком случае не заявляется. Исключения или пропуски для заменённых семи проверок в локальную команду не добавлялись.

Playwright считает конечный результат теста, а не каждую попытку как новый тест. Успешный повтор отмечается как нестабильный; пропущенные и прерванные тесты различаются. Ожидаемое падение (`test.fail`) не считается неожиданной ошибкой. `--list` по-прежнему только перечисляет найденные тесты, без исполнения и без сообщения об успешном прохождении.

- Прямые `test:vitest`, `test:vitest:watch` и `test:vitest:coverage` сохраняют обычный интерфейс Vitest. Coverage создаёт текстовый и HTML-отчёт в `coverage/` (открыть `coverage/index.html`).
- Общий Playwright сохраняет стандартную папку `test-results`; при сбое — trace, screenshot и video.
- Склад сохраняет `test-results/sklad-items` и HTML-отчёт `playwright-report/sklad-items`; trace, screenshot и video не отключаются. Краткий репортёр заменяет только консольный `list`.
- Дизайн-система сохраняет `test-results/design-system`, при сбое — trace и screenshot. Эталоны находятся рядом с тестами в `*.spec.js-snapshots`, допустимая доля отличающихся пикселей — `0.01`.
- Отдельные команды `test:e2e:sklad` и `test:e2e:design-system` также используют краткий репортёр; их подробный отчёт создаётся в `test-reports/summary/playwright-*` в корне репозитория.

В интерактивном терминале краткий отчёт использует цвета: успешные проверки — зелёный, ошибки — красный, пропуски/отмена/нестабильность — жёлтый. Цвета включаются стандартным `node:util.styleText` с учётом TTY и переменных `NO_COLOR`, `FORCE_COLOR`, `TERM`; при обычном перенаправлении вывода цвет отключается. Формат JSON и данные подробных отчётов от оформления консоли не зависят.

Настройка консольного отчёта не меняет сценарии тестов, ответы API или правила прохождения. Playwright с настоящим API по-прежнему нельзя запускать при подключении Laravel к боевой БД.

Открыть уже созданный складской HTML-отчёт:

```bash
npx playwright show-report playwright-report/sklad-items
```

Если изменение внешнего вида ожидаемо и проверено, обновить только нужный эталон:

```bash
npm run test:e2e:design-system -- tests/e2e/design-system/jacoSelect.visual.spec.js --update-snapshots
```

Обновление baseline записывает файлы в репозиторий: его нужно делать осознанно, а не использовать для скрытия неожиданного расхождения. Стабильность сравнения зависит от браузера, ОС и шрифтов. `coverage`, `test-results` и `playwright-report` исключены из Git; эталоны скриншотов отслеживаются.

## Что запускает CI

[unit-tests.yml](../.github/workflows/unit-tests.yml) — отдельный workflow **Chef Unit Tests**, запускающийся при push в любую ветку и при открытии, обновлении или повторном открытии PR. На GitHub-hosted `ubuntu-24.04` с **Node.js 24.13.1** он выполняет `npm ci`, затем **`npm run test:unit`**: прежний Node-набор и Vitest, без исключений и без подавления ошибок. Последний подтверждённый локальный результат этой команды — **448/448**; фактический статус GitHub Actions нужно смотреть у конкретного push/PR.

Краткий итог выводится в журнал шага **Run all unit tests**. Структурированные отчёты и полные журналы из `test-reports/summary/` сохраняются в артефакте **unit-test-reports** на 7 дней, в том числе при падении тестов. Если установка зависимостей завершилась раньше запуска тестов, отчётов может не быть. Новый запуск того же события и ветки/PR отменяет устаревший. E2E, браузеры, сервер и БД этому workflow не нужны.

Прежний [frontend-checks.yml](../.github/workflows/frontend-checks.yml) — отдельный переиспользуемый workflow проверок публикации. [production-image.yml](../.github/workflows/production-image.yml) вызывает его по закреплённому SHA. Эта схема не менялась: прежний шаг использует **Node.js 22** и `node --test tests/unit/*/*.test.mjs`, а не объединённую команду `test:unit`; также выполняется существующая проверка синтаксиса. Vitest подключён в новом unit workflow, а не в закреплённой проверке публикации. Playwright в этих workflows не запускается.

В команде прежнего workflow перечислены восемь исторических исключений `--test-skip-pattern` по точным именам проверок исходников графика. Комментарий workflow помечает их как уже падающие на `main`:

1. `both table variants use capability; open/save and modal lifetime use current graph identity`
2. `desktop and mobile use the same gate, accessible whole-cell actions and editable-only cues`
3. `day modal and page independently defend cached edit flags and stale context`
4. `desktop and mobile hide quick controls and checkboxes without access; revoked selection is cleared`
5. `finance, month and export entry/save handlers recheck rights without caller-role authority`
6. `normal/sticky and mobile team-bonus headers reuse the period modal and obey edit/blur gates`
7. `quick controls and mutation lifecycle share the selected-half date guard`
8. `revoking finance reads closes cached financial modals and invalidates pending day/month reads`

Новый unit workflow, локальные `npm run test:unit` и `npm run test:legacy` эти исключения не добавляют. Поэтому результат прежних проверок публикации может отличаться. Актуальная команда исторических исключений находится в прежнем workflow; этот список не является подтверждением успешного прогона остальных тестов.
