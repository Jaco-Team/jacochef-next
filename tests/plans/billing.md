# Сценарии тестирования Накладных

Актуально на **27.11.2026**. Это сохранённый и уточнённый по коду список сценариев из обсуждения задачи «Внедрить автоматизированное тестирование Шефа». Он задаёт будущие проверки поведения через Vitest и React Testing Library. **Наличие строки в плане не означает, что тест уже написан или прошёл.**

Общие команды и правила окружения описаны в [tests/README.md](../README.md). E2E в текущий этап не входят.

## Как читать план

- **P0** — права, сохранение, суммы и защита от ошибочных записей; проверять первыми.
- **P1** — остальные действия и устойчивость интерфейса.
- **Покрыто** — весь результат строки проверяется существующим тестом. **Частично** — проверен только указанный фрагмент. **Запланировано** — соответствующего поведенческого теста пока нет.
- **RTL** — Vitest + React Testing Library: настоящая страница/компонент и реальные обработчики, подменённые ответы API и внешние браузерные границы. **Unit API** — существующая изолированная проверка общего клиента, не целого модуля.

В страницах создания и редактирования store и расчётные функции определены внутри файлов и не экспортируются. Поэтому ниже расчёты также проверяются через ввод и результат в настоящем интерфейсе. Вынос функций для отдельных unit-тестов — отдельное согласованное изменение приложения, а не часть подготовки окружения. Проверки текста исходников, регулярные выражения и заглушки бизнес-логики не заменяют эти сценарии.

## Фикстуры и границы подмены

Подготовить минимальные валидные ответы каждого реально вызываемого метода: bootstrap списка, справочники точки/поставщика/основания, список со сводкой, `get_one/get_one_bill_ex`, успешное/отклонённое сохранение, OCR и сверка. Для каждого сценария использовать только поля, читаемые его страницей; ID документа/товара/точки должны различаться, чтобы обнаружить смешение контекста.

Нужны документы с несколькими позициями, дублями одного товара с разной ценой, дробными суммами и разными фасовками; выданные/отсутствующие `acces/upd_access`; новые/сохранённые основные изображения и счёт-фактура; очереди Dropzone с success/error/status 0; отложенный ответ для повторного клика; OCR-строки готовые и требующие ручной проверки. Даты и таймеры фиксировать внутри тестов, localStorage очищать.

API подменяется через MSW или конкретную границу клиента; загрузка OCR, хранилище файлов, Dropzone и навигация — управляемыми фикстурами/подменами. Нельзя заменять весь store, расчёты, проверку прав или сами обработчики заглушкой и затем считать сценарий проверенным. Неизвестный HTTP-запрос должен падать по общей настройке окружения. Реальная запись в БД, доставка в 1С, качество серверного OCR и настоящая геометрия просмотрщика не подтверждаются этими тестами.

## Найденные вопросы к реализации

Это замечания после чтения кода, не исправленные и не подтверждённые новыми тестами:

1. В bootstrap списка/карточек и `Pages.useEffect` нет полноценной локальной обработки ошибок/проверки формы ответа. `api_laravel` может вернуть `undefined` после перехваченной ошибки, а страницы затем обращаются к `result.data` или полям ответа. B03 сначала должен воспроизвести это поведение; не подгонять ожидаемый результат под падение.
2. `Billing_.getLocalStorage` выполняет `JSON.parse` без обработки повреждённого значения. Требование устойчивости к испорченному сохранённому фильтру пока не реализовано; добавление защиты — отдельная правка приложения.
3. Обработчики сверки считают отсутствие исключения успехом и не проверяют бизнес-флаг ответа перед уведомлением. B52 должен отличать HTTP-ошибку от `st: false`.
4. Видимость действий edit определяется правами в UI. Отдельные изменяющие методы не доказывают повторную авторизацию на сервере и не заменяют её; тесты не должны заявлять такую гарантию.
5. Различия new/edit по отсутствующему НДС и неоднозначному upload следует зафиксировать отдельными кейсами, а не принудительно приравнять реализации. Бизнес-правило изменения этих различий согласовывается отдельно.

Порядок реализации: P0 фильтров/идентификаторов и сохранения → позиции/суммы/права → файлы/OCR/сверка → оставшиеся P1. Ошибка поведения остаётся видимой и обсуждается отдельно; код приложения в рамках этого плана не меняется.
