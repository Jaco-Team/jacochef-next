## Verified product findings

### 1. Complaint source and order origin are separate concepts

The persisted complaint `source` is currently derived only from the actor role and has two values: `contact_center` and `cafe`. This matches Task §12: statistics for Contact Center and Café must sit in one section without mixing their indicators.

A site order must not be added as a third complaint source merely because it was placed on the website. Task §11 requires **order origin** in the opened order: client, contact center, cashier, or another source, plus the employee name where applicable. The current v2 complaint/read model does not expose those order-origin fields in journal or complaint details. This is a separate backend and frontend gap.

**Required fix:** add an immutable order-origin projection to the order/complaint read model, show it in the order detail, and keep `source` limited to the complaint registration channel. Add an extra statistics dimension only if the business explicitly asks for a breakdown by order origin.

### 2. Filter intent is currently mixed

The same `JacoSearch` control is inside the filter form and triggers a delayed request. That conflates two different actions:

- the form needs an explicit `Номер заказа` text field that becomes part of the server filter submitted with `Применить`;
- the result list needs a separate `JacoSearch` for an immediate, debounced filter by order ID.

**Status:** remediated in the current working tree. `Номер заказа` is a plain field in the submitted form; a separate debounced `JacoSearch` above the results narrows visible rows by order ID without mutating city, café, dates, or submitted filters. The server-side exact lookup continues bypassing the reporting date range.

### 3. Registration cannot currently be completed locally

The Registration empty state tells a user to adjust filters or find an order, but the default local scope returns none. The task-critical flow—open order, add position/order-wide errors, select stage and solution, save complaint, inspect history—could not be proven in this audit.

**Required fix:** restore the reachable local database or seed a known permitted order and catalog data, then execute the complete flow without touching production.

### 4. Journal delivery remains incomplete against Task §10–11

The empty state is understandable, but no saved rows were available to validate required retained and added columns, status colors, promo counts, amounts, resolver, common comment, or order-origin fields. The current read model must not be considered task-complete until that data is available and visually checked on desktop and mobile.

### 5. Statistics needs real-data verification

The layout correctly presents the requested top-level KPI labels and separate source selector. Category expansion, unique-order counting, error totals, shares, employee filtering, and separation of Contact Center from Café cannot be validated without local complaint fixtures.

## UI and accessibility findings

- Mobile spacing, labels, and touch-sized primary action are readable in the captured empty states.
- The compact tab wrapper is visually dense without the prior trailing lower gap.
- Chrome emitted a React warning that `MenuListProps` reaches a DOM element. This is a design-system integration defect and should be resolved in the relevant shared select/menu component with a consumer audit before changing it.
- Chrome emitted an HMR runtime warning in development. It does not prove a module behavior defect, but it should not be used as evidence of a clean dev runtime.
