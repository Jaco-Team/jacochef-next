# Решение: единый модуль «Регистрация ошибок»

## Решение задачи

Новый модуль не заменяет журнал заказов списком технических сущностей. Он добавляет к существующему заказу устойчивую жалобу и её ошибки, сохраняя текущий поиск, детали заказа и исторические данные старых модулей. Новая запись является источником истины для нового процесса; legacy-данные остаются read-only источником истории и переходной отчётности.

## Границы домена

### Жалоба

Жалоба принадлежит одному заказу и кафе. Она содержит общий комментарий, рабочий статус, автора, решение, решившего сотрудника, маршрутизацию в кафе и аудит. Одна жалоба может содержать несколько ошибок.

### Ошибка жалобы

Ошибка принадлежит жалобе и имеет один объект: позиция блюда, доп, столовый прибор, доставка или весь заказ. Для позиции хранится ключ позиции и снимок товара. Для каждой ошибки отдельно сохраняются категория, тип ошибки, ошибка, ингредиент при необходимости, этап, решение, комментарий, сумма ошибки и сумма изменения.

Несколько ошибок одной позиции — отдельные записи, а не счётчик одной записи. Это позволяет независимо менять этап, решение и аудит.

### Настройки «Варианты решения жалоб»

Классификатор новой жалобы хранится только в `errors_management_catalog_nodes` как явное дерево «Категория → Тип ошибки → Ошибка». Категория имеет правило одного типа объекта, для допов — явные идентификаторы категорий сайта; ошибка может требовать продукт из состава. Это исключает adapter к `err_desc_cats` и не переносит неявную legacy-семантику в новый процесс.

Этапы и решения — самостоятельные узлы того же раздела настроек «Варианты решения жалоб» с активностью, порядком, описанием и аудитом. Историческая запись хранит снимок названий и идентификаторы, поэтому отключение узла не ломает прошлые жалобы.

## Данные и миграция

Одна миграция задачи в `mysql_jaco_main_rolls` создаёт все новые таблицы и индексы: жалобы, ошибки жалоб и настраиваемые узлы справочника. Аудит жалоб и настроек использует общий `jaco_site_rolls.change_events`, без второй task-specific таблицы событий. Она не удаляет и не переписывает `err_orders`, `err_order_price_users`, `err_win_orders`, `fines_err` или их истории.

До написания миграции backend фиксирует точные ключи legacy-таблиц и решает для каждого отчётного поля: новый источник, legacy-read projection или объединённая агрегация. Повторные временные схемы запрещены.

## API

API разделяется на read-model и команды.

- Bootstrap возвращает доступные кафе, справочники, права и настройки.
- Заказ возвращает существующие сведения заказа, состав и позиции, дополненные сохранёнными жалобами.
- Journal возвращает строки сохранённых жалоб с серверными фильтрами, сортировкой и пагинацией; сведения заказа подгружаются для этих строк.
- Create/update error принимают только идентификаторы и проверяют принадлежность позиции заказу, ингредиента составу товара, активность классификатора, этапа и решения.
- Workflow-команды отправляют в кафе, принимают и решают жалобу. Каждая команда проверяет точку, роль и допустимый переход.
- Settings-команды создают и изменяют классификатор, этапы и решения с аудитом.
- Statistics возвращает KPI и раздельные агрегаты КК/кафе.

Переходы проверяют версию жалобы и записываются в аудит; повторное создание жалобы создаёт новую запись. API не принимает пользовательские снимки названий, статусов или сумм как источник истины.

## Авторизация и маршрутизация

Доступ проверяется на каждой операции по кафе. Пользователь кафе читает только свои точки; региональный директор — точки своего региона; КК — данные в пределах предоставленного доступа. Кафе назначения берётся из заказа, не из client payload. Пока жалоба рассматривается в кафе, UI не показывает сумму изменения как удержание. Расчёт зарплаты по-прежнему читает только существующие `err_orders`/`fines_err`; подключение v2 требует отдельного подтверждённого события удержания и не подменяется UI-флагом.

## UI

Журнал остаётся заказным рабочим экраном. Фильтры используют доступный выбор кафе, а не свободный ввод. Поиск расположен над таблицей. Детали жалобы открываются в responsive drawer; пустая область не резервируется.

Регистрация имеет один путь: открыть заказ → добавить ошибку позиции или ошибку заказа → заполнить каскадный классификатор → ингредиент при необходимости → обязательный этап → комментарий → сохранить; решение выбирается при рассмотрении жалобы. Кнопки массового неясного режима и режим описания ошибок удаляются.

Вкладка «Варианты решения жалоб» — статичное дерево настроек с активной и неактивной группами. Верхний порядок фиксирован: Блюдо, Заказ, Допы, Столовые приборы. Фронтенд использует только подтверждённые поля API; до готовности команды не показывает фиктивный результат сохранения.

1. Backend domain/read-model contract и одна миграция.
2. Backend feature tests: доступ, объект заказа, состав, несколько ошибок, этап, аудит, переходы, legacy-read и статистика.
3. Frontend journal и order detail на новом read-model.
4. Frontend registration и settings на write contract.
5. Frontend workflow, statistics и Contact Center New cleanup.
6. Chrome desktop/mobile проверка на локальном API и локальной БД.

Каждый этап заканчивается только когда код, API contract, tests и документы согласованы.
