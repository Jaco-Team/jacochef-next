# UX review: «Регистрация ошибок»

## Основание и метод

Проверка проведена 29.09.2026 по локальному модулю в уже открытом Chrome. Продакшн `jacosoft-dop.ru` использовался только как read-only источник поведения. Требования ТЗ являются критерием решений ниже.

Снимки проверки сохранены вне репозитория:

- `/tmp/errors-management-ux-audit/01-statistics-desktop.png` — исходный раздел статистики;
- `/tmp/errors-management-ux-audit/02-journal-desktop.png` — исходный журнал;
- `/tmp/errors-management-ux-audit/03-registration-desktop.png` — исходная регистрация.

Проверка drawer с сохранённой жалобой не выполнена: локальная база не содержит жалоб. Данные не создавались специально для визуальной проверки.

## Целевой пользовательский путь

1. **Регистрация** — сотрудник находит существующий заказ, открывает его и добавляет одну или несколько ошибок позиции либо ошибку всего заказа. Это единственный вход для создания жалобы.
2. **Журнал** — сотрудник ищет уже сохранённые жалобы, открывает их в правой панели и видит статус, ошибки и историю.
3. **Статистика** — сотрудник сначала явно задаёт город, кафе, период, источник и сотрудника, затем получает только результаты этих фильтров. Показатели КК и кафе показаны раздельно.

Вкладки соответствуют трём разным намерениям пользователя. Фильтры не переносятся скрыто между ними: одинаковые базовые значения разрешены только как видимые значения формы активной вкладки.

## Визуальные правила модуля

- Использовать `container_first_child`, стандартный заголовок модуля, MUI `Tabs`, `Paper`, `Grid`, `Button` и существующие JACO controls.
- Внутри каждой `Paper`-панели всегда есть padding; граница не должна прилипать к полям формы или тексту.
- Кафе выбирается только селектором среди доступных точек, свободный ввод запрещён.
- Основное действие формы — contained кнопка; обновление модуля остаётся вторичным outlined действием.
- Инструкции показываются только когда объясняют состояние или действие. Технические описания процесса в UI не выводятся.
- Desktop использует таблицу для сравнения строк; mobile — карточки с теми же действиями и без горизонтальной прокрутки.

## Непрерывная сверка с ТЗ

Перед следующим крупным изменением сверять реализацию с `TARGET_BP.md` и `PLAN.md` в этом каталоге. Нельзя закрывать этап по визуальному наличию экрана: он завершён только когда контракт, доступ, данные, audit и проверка сценария соответствуют пунктам ТЗ.
