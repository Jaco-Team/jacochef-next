# Регистрация ошибок

## Назначение

Модуль ведёт жалобу по заказу от регистрации до решения. Он нужен контакт-центру и кафе для общей фиксации ошибок заказа, контроля маршрутизации, аудита и аналитики. Одна жалоба объединяет несколько независимых ошибок позиции или заказа, но не заменяет исходные данные заказа.

## Рабочий контур

- `Журнал жалоб` — серверный список жалоб по доступным кафе, поиск заказа, фильтрация, сортировка, пагинация и детали.
- `Регистрация` — поиск заказа и единый путь: ошибка позиции либо ошибка заказа, классификатор, этап, решение, сохранение.
- `Статистика` — уникальные заказы с ошибками, количество ошибок, категория/тип, раздельные каналы регистрации.
- `Варианты решения жалоб` — настройки категорий, типов ошибок, ошибок, этапов и решений с фиксированным деревом, активностью, порядком и историей.

## Данные и ответственность

Новые жалобы хранятся в `mysql_jaco_main_rolls`:

- `errors_management_complaints` — заказ, кафе, маршрут и статусы;
- `errors_management_complaint_errors` — отдельные ошибки и снимки классификатора;
- `errors_management_catalog_nodes` — настройки раздела «Варианты решения жалоб».

Заказ, позиции и состав блюда остаются источниками существующих БД точек и сайта. Исторические `err_orders`, `err_order_price_users`, `err_win_orders` и `fines_err` не переписываются модулем.

## Правила регистрации

- Одна жалоба относится к одному заказу и содержит любое число самостоятельных ошибок. Ошибка позиции и общая ошибка заказа — разные объекты: для общей ошибки используется только категория `Заказ`, без позиции.
- Для блюда backend получает состав товара сайта. Если ошибка требует ингредиент, пользователь выбирает продукт состава до этапа и решения. Этап обязателен, а решение является последним полем ошибки.
- Категория определяется по объекту заказа: блюдо, доп, доставка или заказ. Единственный активный вариант следующего уровня выбирается автоматически; при отсутствии варианта интерфейс сообщает, что настройка не выполнена.
- Статус жалобы проходит `registered → sent_to_cafe → accepted_by_cafe → resolved`. Жалоба, созданная ролью кафе, сразу находится в контексте рассмотрения кафе.

## Контракт API

Frontend получает доступные города, кафе и права через legacy `get_all`, ищет заказы через legacy `get_orders` и ведёт новый процесс через v2 endpoints: `context`, `create`, `journal`, `statistics`, `detail`, `transition`, `settings`, `settings/save`, `settings/history`. Маршрутизация, проверка кафе, прав действий, статусов и optimistic lock выполняются на backend; `src/api_new.js` не содержит специальной логики модуля.

Для новой ошибки позиции backend сохраняет `position_name` — человекочитаемое имя строки заказа на момент регистрации; детали показывают его при наличии, а исторические записи без снимка не подменяются техническим `position_key`.

Снимок заказа в деталях сохраняет рабочие сведения: кто оформил, тип, клиент, адрес доставки, сумма, оплата, сотрудник и комментарий клиента. Клиент определяется только по совпадению связанной учётной записи сайта и номера заказа; без него доставка и самовывоз относятся к контакт-центру, заказы зала — к кафе. Канал регистрации жалобы (`contact_center` или `cafe`) является отдельным полем и не зависит от источника заказа.

## Авторизация

Все чтения и команды ограничены доступными кафе. Кафе назначения определяется сервером по заказу. Действия рассмотрения доступны только ролям кафе по разрешённым точкам; региональный руководитель использует свой региональный набор точек. Редактирование настроек требует capability `errors_management_settings_edit`.

## Статусы

`registered` → `sent_to_cafe` → `accepted_by_cafe` → `resolved`.

Переходы выполняются серверными командами с optimistic lock и аудитом. Пока жалоба находится у кафе, интерфейс не показывает сумму изменения как удержание.

## Зарплата и регламент

Расчёт зарплаты сотрудников остаётся в `staff_schedule`: он читает исторические `cafe_users_bonus_err`/`err_orders` и `fines_err`. Ночная задача `cafe:cron-update-cafe-wages` применяет ставки и не обрабатывает жалобы. Новая v2-жалоба пока не создаёт удержание; для этого нужен отдельный утверждённый контракт распределения суммы по сотрудникам и исключения двойного учёта.

## Локальная среда и границы данных

Для локального frontend явно задаётся `NEXT_PUBLIC_API_URL=http://127.0.0.1:8000/api` в `.env.development`: общий `api_laravel` при отсутствии переменной имеет production fallback. Перед записью в локальную БД сверяются эффективные адрес API и DB_HOST/DB_PORT работающих процессов.

Локальная разработка использует backend с `DB_HOST=127.0.0.1` и `DB_PORT=3307`; перед SQL-проверкой применяется project wrapper `.codex/skills/jaco-db-connections/scripts/mysql-env.sh local`. Он не предназначен для production-изменений. Локальные данные допускаются только для проверки сценария и не отправляются в production.

При завершении жалобы пользователь может указать уже выданный клиенту промокод. v2 сохраняет снимок кода и принимает технический ID выдачи от интеграции, если он доступен; активации считаются только по сохранённому ID в `promo_orders_center`. Модуль не создаёт и не меняет legacy-промокоды и не устанавливает связь эвристикой по заказу, названию или времени. KPI модуля строятся только по v2-жалобам; `stat_err_cash`, `fines` и `fines_err` остаются независимыми legacy-отчётами.

## Проверка

Перед приёмкой пройти сценарий на локальном API и БД: найти заказ → добавить несколько ошибок позиции и ошибку заказа → сохранить → отправить в кафе → принять → решить → проверить журнал, аудит и статистику. Подробный текущий статус — в `PLAN.md` и `TASK_VALIDATION_2026-09-30.md`.
