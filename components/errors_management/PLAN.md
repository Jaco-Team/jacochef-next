# План доработки интерфейса «Регистрация ошибок»

## Принцип выполнения

Работа начинается с frontend, но frontend не подменяет отсутствующие бизнес-данные выдуманными полями или локальным сохранением. Сначала сохраняется полезный существующий поиск и просмотр заказа, затем интерфейс переводится на подтверждённый контракт новой жалобы. Backend меняется только после фиксации требуемого frontend-контракта в backend handoff.

## Контрактные ограничения

- Нельзя заменять журнал заказов коротким списком жалоб.
- Нельзя удалять из существующего журнала поля, кроме прямо перечисленных в ТЗ.
- Поле точки всегда выбирается из доступных пользователю кафе; свободный ввод идентификатора запрещён.
- Нельзя показывать технические значения, внутренние коды или пустую имитацию деталей вместо бизнес-данных.
- Нельзя считать локальное состояние диалога сохранённой жалобой.

## Этап F1. Сохранение рабочего журнала и фильтров

- [ ] Оставить текущий поиск заказов и открытие карточки заказа.
- [ ] Использовать единый контрол выбора кафе, ограниченный доступными точками; переименовать пользовательскую подпись «Точка» в «Кафе».
- [ ] Сохранить поиск по номеру заказа, клиенту, периоду, сумме и типу заказа, если endpoint подтверждает соответствующий фильтр.
- [ ] Привести каркас страницы, заголовок, вкладки, панели фильтров, отступы и мобильный вид к действующему Chef design system без глобальной правки legacy-компонентов.
- [ ] Сохранить доступ к полной существующей информации заказа в карточке.

Критерий приёмки: пользователь с доступом видит только свои кафе, находит заказ, открывает его и получает существующие данные без потери полей.

## Этап F2. Понятный сценарий регистрации

- [ ] Убрать режим описания ошибок и локальный переключатель, создающий два сценария.
- [ ] Сделать один явный вход: открыть заказ → выбрать позицию или «Ошибка по заказу» → добавить одну или несколько ошибок → заполнить обязательные поля → сохранить жалобу.
- [ ] Добавить отдельную сущность «Ошибка по заказу» из ветки «Заказ»; не предлагать её для блюда.
- [ ] Разрешить несколько записей ошибок на одной позиции и показать их в составе заказа.
- [ ] Отображать состав блюда из backend, когда выбран вариант качества ингредиента; расположить поле ингредиента выше этапа и решения.
- [ ] Всегда размещать поле решения последним в форме ошибки.
- [ ] Использовать ровно три пользовательских уровня: «Категория», «Тип ошибки», «Ошибка».
- [ ] Реализовать последовательное автозаполнение только по подтверждённым доступным вариантам; при отсутствии вариантов показать текст из ТЗ.
- [ ] Добавить обязательный этап возникновения ошибки и описание этапа рядом с выбором.

Зависимость: backend должен вернуть нормализованные активные категории, типы, ошибки, решения, этапы и описание этапа, а также принять несколько ошибок одного заказа.

Критерий приёмки: один пользователь последовательно регистрирует одну ошибку блюда, две ошибки одной позиции и одну ошибку заказа; форма не позволяет отправить без обязательных данных.

## Этап F3. Журнал жалоб и детали

- [ ] Построить журнал на заказах с ошибками, сохранив существующие колонки кроме перечисленных к удалению.
- [ ] Добавить: выписано промокодов, активировано промокодов, общий комментарий, кто решил жалобу, статус жалобы, сумма ошибки, сумма изменения.
- [ ] Добавить понятную цветовую индикацию статусов «В решении» и «Решена» после утверждения backend-статусов.
- [ ] Открывать подробности заказа и жалобы в адаптивной панели; не занимать постоянную половину экрана пустым состоянием.
- [ ] Показать оформителя, ФИО сотрудника-оформителя и комментарий клиента вместе с существующими сведениями заказа.
- [ ] Показать аудит жалобы только после фактического сохранения на backend.
- [ ] Добавить серверную сортировку, поиск и пагинацию только после согласования параметров endpoint.

Зависимость: backend read-model должен вернуть объединённые order/complaint данные, стабильные статусы, аудит и метаданные пагинации.

## Этап F4. Настройки

- [ ] Перестроить настройки в статичное дерево «Категория → Тип ошибки → Ошибка».
- [ ] Зафиксировать верхний порядок: Блюдо, Заказ, Допы, Столовые приборы.
- [ ] Отдельно показать активные раскрытые и неактивные свёрнутые элементы с количеством и быстрым переключением состояния.
- [ ] Добавить отдельные настройки этапов с описанием.
- [ ] Добавить отдельный справочник решений: название, описание, порядок, активность, активная и неактивная группы.
- [ ] Показать аудит изменений настроек.

Зависимость: отдельные backend-сущности настроек, порядок, активность и аудит. Старый `option_to_win` не является достаточным контрактом.

## Этап F5. Рассмотрение и статистика

- [ ] Показать действие «Отправить в кафе для принятия решения» с автоматически определённым кафе перед подтверждением.
- [ ] Разрешить действия кафе только уполномоченным ролям и показывать только доступные точки.
- [ ] Показать решившего сотрудника и дату решения.
- [ ] Показать два KPI: уникальные заказы с ошибками и общее количество ошибок.
- [ ] Добавить раскрываемую разбивку по категориям и типам ошибок: уникальные заказы, ошибки, доля.
- [ ] Добавить фильтры город/кафе, даты и сотрудник; раздельные несмешиваемые показатели КК и кафе.

Зависимость: backend-команды маршрутизации, ролевой доступ, состояние расчёта зарплаты и агрегированная статистика.

## Проверка перед каждым крупным commit

- [ ] Проверить API payload в браузерной сети на локальном API.
- [ ] Проверить desktop и mobile через уже запущенный Chrome и локальный frontend.
- [ ] Добавить целевые unit/component tests для новой формы и backend feature tests для соответствующих endpoint.
- [ ] Проверить, что frontend не обращается к production API и backend использует локальную БД в dev окружении.
- [ ] Обновить README модуля после реализации, не до неё.
