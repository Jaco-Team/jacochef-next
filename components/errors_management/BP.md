# Текущий бизнес-процесс: «Регистрация ошибок»

## Назначение и границы

Текущий модуль позволяет сотруднику найти заказ, открыть его состав и подготовить в интерфейсе черновой набор проблем по выбранным позициям. Модуль одновременно показывает и настраивает устаревший справочник причин через `option_to_win`.

Это описание фиксирует фактическое поведение на момент начала доработки. Оно не описывает целевое состояние ТЗ и не подтверждает сохранение жалобы в постоянном хранилище.

## Участники и доступ

- Авторизованный сотрудник получает города, доступные точки, классификатор, этапы, варианты решения и набор прав из `get_all`.
- Доступ к номеру телефона и режиму работы с ошибками заказа определяется полями `tel_access` и `err_order_mod_access`.
- Список точек ограничивается текущими правами пользователя через `Helper::getMyPoints`.

## Поиск и журнал заказов

1. Пользователь выбирает город, точку или все точки города, тип заказа, номер заказа, телефон, сумму и период.
2. Frontend отправляет фильтры в `errors_management/get_orders`.
3. Backend читает заказы из БД точки, рассчитывает производственные и доставочные показатели, объединяет их с частью статистики и возвращает массив заказов.
4. Frontend отображает широкую таблицу заказов. Номер заказа открывает карточку заказа.

В таблице сейчас показываются заказ, оформитель, клиент, адрес, временные операционные показатели, тип, статус заказа, сумма, оплата и водитель. В ТЗ требуется сохранить только не перечисленные к удалению сведения и добавить поля жалобы; такого журнала пока нет.

## Карточка заказа

1. Frontend запрашивает `errors_management/get_order_new` по точке и заказу.
2. Backend возвращает сведения заказа, состав, позиции для ошибок, доставку, информацию о водителе и дополнительные признаки заказа.
3. Карточка показывает информацию о заказе и состав.
4. При включённом локальном режиме ошибок сотрудник выбирает одну или несколько позиций флажками либо открывает позицию кликом.
5. Открывается диалог `ModalProblems`.

Текущий переключатель режима ошибок хранится в `localStorage`. Он создаёт два конкурирующих способа начать регистрацию: выбор флажками с действием для N позиций и клик по позиции. Это соответствует отмеченной в ТЗ проблеме понятности процесса.

## Черновик ошибки позиции

Для каждой выбранной позиции диалог строит дерево активных листовых узлов старого справочника. Он фильтрует варианты по категории сайта позиции, пытается автоматически выбрать корневой узел и предлагает вариант решения, комментарий, количество и фото.

Если выбрана ветка «качество ингредиентов», диалог показывает ингредиенты, полученные backend из состава товара сайта. Сейчас поле ингредиента расположено после варианта решения, а названия уровней зависят от глубины старого дерева. Поля обязательного этапа возникновения ошибки нет.

Нажатие «Применить» сохраняет результат только в состоянии открытой карточки заказа. Backend не получает команду создания жалобы. При закрытии карточки этот результат исчезает.

## Ошибка заказа и множественные ошибки

- В API и интерфейсе нет отдельной устойчивой регистрации ошибки на весь заказ.
- Для позиции поддерживается одно объединённое состояние проблемы; несколько самостоятельных ошибок для одной позиции не сохраняются.
- Доставка добавляется как техническая позиция для заказа доставки.

## Справочник причин и решений

Вторая вкладка показывает старый древовидный справочник `option_to_win`. Через него можно создавать, редактировать, активировать и удалять категории. Порядок дерева не фиксирован. Нет отдельной группировки активных и неактивных элементов, истории настроек, отдельного справочника решений с сортировкой и описанием этапов.

## История, маршрутизация и статистика

В текущем модуле отсутствуют постоянные сущности жалобы, история её создания и изменений, передача в кафе, принятие и завершение рассмотрения, фиксация решившего сотрудника, удержание из зарплаты и отдельная статистика жалоб. Поэтому эти данные не могут корректно появиться в журнале, деталях или отчётах.

## Связи данных

- `jaco_main_rolls`: города, точки, пользователи, доступы и старый классификатор.
- БД точки: заказ, позиции заказа, статусы и операционные данные.
- `jaco_site_rolls`: товары сайта и составы, из которых backend строит ингредиенты позиции.
- `option_to_win`: устаревшие настройки причин и вариантов решения.

## Связанный текущий процесс жалоб и удержаний

Помимо экрана регистрации, в кодовой базе существует отдельный процесс обработки ошибок через `jaco_site_rolls.err_orders`, `err_order_price_users` и `err_win_orders`, а также через `jaco_main_rolls.fines_err`. Его отчётный экран `stat_err_cash` читает закрытые ошибки по точке и периоду, позволяет просмотреть историю, изменить сумму или исключить запись при обязательном текстовом обосновании.

История этого процесса хранится отдельно: `err_order_price_users_history` и `fines_err_history`. Запись `fines_err` содержит точку, статус, сотрудника, сумму, изменение суммы, ответ и дату решения. Этот процесс не является единым журналом жалоб: данные по заказу, решению, удержанию и истории распределены между несколькими таблицами и разными модулями. ТЗ требует объединённый пользовательский процесс, но исторические записи и правила расчёта нельзя потерять или переопределить без отдельно подтверждённого переноса.
