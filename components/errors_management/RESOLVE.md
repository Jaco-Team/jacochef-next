# Нерешённые вопросы модуля «Регистрация ошибок»

Документ описывает вопросы, которые нельзя закрыть корректной реализацией без правила владельца процесса или подтверждённой связи данных. Они не являются поводом подменять данные эвристиками.

## Принятые решения — 05.10.2026

1. При решении жалобы можно указать уже выданный клиенту промокод. v2 сохраняет точный код и, если его передаёт выдающий процесс, технический ID выдачи. Количество активаций определяется только по сохранённому ID через `promo_orders_center`. v2 не создаёт и не редактирует legacy-промокоды, не выводит ID из номера заказа, названия или времени.
2. Статистика модуля строится только по v2-жалобам. В одном разделе остаются раздельные каналы «Контакт-центр» и «Кафе»; legacy `stat_err_cash`, `fines` и `fines_err` продолжают работать как независимые отчёты и не смешиваются с KPI v2 без ключа заказа и канала.
3. Вход в v2 использует действующую модель: аутентифицированный пользователь работает только в доступных кафе; сервер проверяет точку для каждой команды. Изменение настроек дополнительно требует `errors_management_settings_edit`. Legacy `err_order_mod_access` не используется и роли не меняются этой задачей.

## 1. Промокоды в журнале жалоб — решено

В v2-жалобе сохраняется снимок кода выданного промокода. Выдающий процесс при наличии передаёт технический ID, по которому `promo_orders_center` подтверждает активацию. Без ID активация не предполагается и отображается как ноль; связи по заказу, названию или времени не строятся. Legacy-выдача не изменяется.

## 2. Единая статистика с legacy-модулями — решено

KPI «Заказов с ошибками», «Всего ошибок», выписанные и активированные промокоды строятся по v2-жалобам. Разрез «Кафе» и «Контакт-центр» остаётся в одном разделе, но источники не суммируются в одну неразличимую строку. `stat_err_cash`, `fines` и `fines_err` остаются отдельными legacy-отчётами.

## 3. Правило входа в новый модуль — решено

Действующая модель доступа принята без изменения legacy-ролей: сервер проверяет доступность точки в каждой v2-команде; редактирование настроек требует `errors_management_settings_edit`. Единственная миграция задачи создаёт capability и выдаёт полное право шаблону приложения `1`; остальным шаблонам создаётся выключенная запись. `err_order_mod_access` не подключается как скрытый fallback.

## 4. Сквозной процесс разными ролями

### Что реализовано

Создание, маршрутизация, принятие, решение, аудит, optimistic lock и ограничение точкой реализованы. В Chrome локально подтверждён путь жалобы кафе: создание → принятие кафе → решение; жалоба №3 содержит ошибку блюда и общую ошибку заказа. Автоматические проверки покрывают правила переходов и валидацию классификатора, но не изолированный HTTP-сценарий с реальной БД.

### Что ещё проверить

Нужны локальные пользователи с изолированными ролями КК, менеджера кафе и регионального директора, а также доступом к разным кафе. На них пройти путь: создать → отправить → принять → решить; подтвердить, что суммы изменения скрыты до решения, журнал и статистика обновлены, а чужая точка недоступна.

### TestAccess

`TestAccess` подходит для development-проверки видимости frontend-элементов: он меняет локальный объект access только в браузере. Он не меняет роль, список доступных кафе или backend-авторизацию, поэтому не заменяет этот сквозной тест.

## 5. Аудит настроек, созданных через интерфейс

### Что известно

Локальный стартовый каталог был засеян напрямую в БД, поэтому у этих строк нет событий создания в `change_events`. Пустая история таких записей ожидаема.

### Что ещё проверить

Локально пользователем 2207 приложения `1` созданы, изменены и отключены варианты через реальное `errors_management_settings_edit`; история показывает автора, изменения и время до минут. Остаётся проверить включение каждого типа, область нескольких кафе и сохранение неактивного варианта в исторической жалобе.

## 6. Окончательная UX-приёмка

### Что реализовано

Исправлены различимость строк журнала, обязательность классификатора и этапа, состав блюда, защита черновика, загрузочные состояния, настройки и адаптивная сетка фильтров.

### Что ещё проверить в Chrome

Desktop, около 930 px и mobile уже пройдены для поиска заказа, регистрации, ошибки заказа, drawer, журнала, статистики и вкладок. Локально подтверждены жалоба №3 с двумя разными областями ошибки и жалоба №4 с двумя ошибками одной позиции. Открыты только сценарии с ролями/кафе, mutation-настроек с правом и позициями «Допы»/«Доставка», которых нет в доступном тестовом заказе.
