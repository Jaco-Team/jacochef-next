# Целевой бизнес-процесс: «Регистрация ошибок»

## Цель

Модуль ведёт одну жалобу по заказу как рабочий процесс от регистрации до решения. Жалоба содержит несколько независимых ошибок: по конкретным позициям заказа и, при необходимости, одну или несколько ошибок всего заказа. Исторические данные старых модулей доступны для чтения и отчётности, но не подменяют новые записи.

## 1. Поиск и открытие заказа

1. Сотрудник выбирает доступное ему кафе, период и параметры поиска. Кафе выбирается только из точек, разрешённых его доступом.
2. Журнал показывает заказы с жалобами. Он сохраняет все прежние колонки, кроме прямо исключённых ТЗ, и добавляет показатели жалобы.
3. Сотрудник открывает заказ и видит текущие сведения заказа, оформителя, ФИО сотрудника-оформителя при наличии и комментарий клиента.
4. В карточке заказа отображаются ранее сохранённые жалобы, ошибки, решения и аудит.

## 2. Регистрация жалобы

1. Сотрудник нажимает «Добавить ошибку» у позиции состава или «Ошибка по заказу».
2. Ошибка позиции всегда привязана к позиции заказа. Ошибка заказа доступна только из раздела «Заказ» и не предлагается для блюда.
3. Для одной позиции разрешено добавить несколько отдельных ошибок. Каждая сохраняет собственные классификатор, этап, решение, комментарий, сумму и историю.
4. Для блюда с ошибкой качества ингредиентов сотрудник выбирает ингредиент из состава товара сайта. Поле ингредиента находится выше этапа и решения.
5. Поля следуют единой терминологии: «Категория» → «Тип ошибки» → «Ошибка» → «Продукт из состава» при необходимости → «Этап возникновения ошибки» → комментарий и вложения → «Решение ошибки» последним полем формы.
6. Этап обязателен. Возле выбора показывается описание этапа. При регистрации можно указать сумму ошибки — зафиксированный денежный эффект инцидента; пустое значение означает, что сумма не определена, а не ноль.
7. Решение и сумма изменения фиксируются при завершении рассмотрения кафе для каждой ошибки. Решение выбирается из активных вариантов; сумма изменения — подтверждённый итог корректировки и тоже может быть неизвестна.
8. Перед сохранением система проверяет доступ к кафе, принадлежность позиции заказу, активность классификатора, допустимость этапа, решения и ингредиента. После успешного сохранения создаётся аудит.

## 3. Автоматический классификатор

1. Тип объекта определяет верхнюю категорию: блюдо, доп, столовый прибор, доставка или заказ.
2. Система выбирает категорию автоматически, если для объекта доступен ровно один вариант.
3. Затем таким же правилом выбирает единственный тип ошибки и единственную ошибку.
4. При двух и более вариантах пользователь выбирает значение сам.
5. При отсутствии доступной настройки выводится «Для выбранной позиции варианты ошибок не настроены».

## 4. Рассмотрение жалобы

1. Жалоба, зарегистрированная КК, получает рабочий контекст «Контакт-центр» и доступна КК по правилам роли. Жалоба, зарегистрированная сотрудником кафе, сразу получает контекст «Кафе рассматривает» в том же кафе: отдельная отправка самому себе не требуется.
2. КК видит кафе, определённое по заказу, и может отправить жалобу в кафе для принятия решения.
3. После отправки фиксируются отправитель, дата и время; жалоба получает статус «В решении» и появляется только у разрешённых сотрудников соответствующего кафе или региона.
4. Кафе принимает жалобу, фиксирует решение и сумму изменения отдельно по каждой ошибке, затем завершает рассмотрение. Фиксируются ФИО решившего сотрудника, дата, время и решение.
5. Статус сохраняет обязательные значения «В решении» и «Решена». Для работы внутри статуса «В решении» журнал показывает понятный контекст: контакт-центр, ожидает принятия кафе или кафе рассматривает; цвет остаётся светло-жёлтым.
6. Пока жалоба находится в решении кафе, сумма изменения не выводится как сумма ЗП.

## 5. Журнал и аудит

Журнал сохраняет не исключённые существующие столбцы и добавляет: выписано промокодов, активировано промокодов, общий комментарий, кто решил жалобу, статус жалобы, сумма ошибки и сумма изменения. Пустая сумма выводится как «—», а не как `0 ₽`. Статус «В решении» отмечается светло-жёлтым, «Решена» — светло-зелёным; контекст КК и кафе показывается текстом, без изменения обязательного значения статуса.

Аудит жалобы показывает создание, каждое изменение с полем и старым/новым значением, отправку в кафе, принятие, завершение и выбранное решение. Неактивные классификаторы, этапы и решения сохраняются в старых записях и аудите.

## 6. Настройки «Варианты решения жалоб»

Вкладка «Варианты решения жалоб» является единым пользовательским разделом настроек. Она ведёт дерево «Категория → Тип ошибки → Ошибка» с фиксированным верхним порядком: Блюдо, Заказ, Допы, Столовые приборы, Доставка. Нижние уровни статичны для пользователя и управляются полем порядка в настройках; активные элементы раскрыты и показаны первыми, неактивные — ниже свёрнутыми. У каждого элемента есть быстрый переключатель и аудит изменений.

Этапы имеют название, описание, активность и историю. Решения имеют название, описание, порядок, активность и раздельные активную/неактивную группы. Неактивные значения недоступны в новой жалобе, но остаются в истории и статистике.

## 7. Статистика

Раздел показывает два KPI: уникальные заказы с ошибками и общее число ошибок. Ниже категории раскрывают типы ошибок; для каждой строки выводятся уникальные заказы, количество ошибок и доля от всех ошибок. Фильтры: город/кафе, период и сотрудник. Показатели КК и кафе находятся в одном разделе, но считаются и отображаются раздельно. Общий read-model объединяет только записи с подтверждёнными идентификаторами заказа и канала; `stat_err_cash` остаётся отчётной проекцией `err_orders` и `fines_err`, а справочник `fines` не является самостоятельным источником событий.

## 8. Контакт-центр нов

Проверка исходного кода «Контакт-центр нов» подтверждает отсутствие выбора и настройки ошибок: `err_info` относится только к контролю времени приготовления и доставки. Модуль не изменяется.
