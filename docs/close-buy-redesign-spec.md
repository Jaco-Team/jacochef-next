# Close Buy — redesign

Статус: дизайн и техническая спецификация готовы к handoff.  
Дата: 29 июля 2026.  
Figma: [Close Buy — redesign](https://www.figma.com/design/IBZGPYXeOgyPA33eBqvOUn)

## 1. Scope

В этом этапе меняются только Figma-макеты и спецификация. Frontend и Laravel-код не изменяются.

Цели:

- ускорить работу с телефона;
- заменить массовую инверсию товаров на явное итоговое состояние категории;
- не показывать локально состояние, которое сервер ещё не подтвердил;
- сделать историю компактной, фильтруемой и пригодной для аудита;
- сохранить MUI, Roboto, `#c03`, существующую палитру и радиусы проекта.

## 2. Семантика состояния

- `is_active = 1` — товар открыт.
- `is_active = 0` — товар закрыт.
- `null`, отсутствующее поле или отсутствующая запись при чтении нормализуются в `0`.

Состояние категории вычисляется из нормализованных товаров:

- `open`: `open_count === total_count`;
- `closed`: `open_count === 0`;
- `mixed`: `0 < open_count < total_count`.

Пустая категория не получает массовое действие. Она отображается как пустое состояние.

## 3. Массовое действие

Массовое действие всегда передаёт серверу конкретное итоговое значение. Инверсия каждого товара запрещена.

| Состояние категории | Основной контрол              | Результат                                                      |
| ------------------- | ----------------------------- | -------------------------------------------------------------- |
| Все закрыты         | `Открыть все`                 | Сразу отправить `is_active: 1`                                 |
| Все открыты         | `Закрыть все`                 | Сначала показать подтверждение, затем отправить `is_active: 0` |
| Смешанное           | `Действия со всей категорией` | Показать `Открыть все` и `Закрыть все`                         |

Открытие выполняется без подтверждения. Закрытие подтверждается:

- на телефоне — `SwipeableDrawer`/bottom sheet;
- на ПК — MUI `Dialog`.

Подтверждение показывает название категории и количество товаров по последнему известному состоянию. Сервер всё равно повторно определяет актуальный состав категории внутри транзакции.

Во время запроса action-контрол блокируется. Повторное нажатие не должно создавать вторую операцию.

## 4. Mobile, 360–430 px

Основной экран:

- заголовок и выбор точки;
- вкладки `Управление` / `История`;
- поиск по товарам и категориям;
- фильтр `Все / Открытые / Закрытые`;
- сводка по точке;
- карточки категорий.

Карточка категории содержит:

- название;
- `Открыто X из Y`;
- текстовый статус `Открыто` / `Закрыто` / `Смешано`;
- один массовый action-контрол;
- раскрываемый список товаров.

Товарная строка содержит название, ID и подписанный `Switch`: `Открыт` / `Закрыт`. Изменение единичного товара применяется сразу.

Минимальная интерактивная зона — `44 × 44 px`.

## 5. Desktop, 1280/1440 px

Используется тот же сценарий:

- слева — список категорий;
- справа — товары выбранной категории;
- сверху — выбор точки, вкладки, поиск, фильтры и сводка;
- подтверждение закрытия — `Dialog`.

Смена viewport не меняет смысл контролов и API-операций.

## 6. История

История вынесена во вкладку `История`.

Mobile:

- карточки событий;
- группировка по дате;
- автор, время, точка, действие, категория/товар и количество;
- раскрытие списка только реально изменённых товаров.

Desktop:

- таблица событий;
- раскрываемая detail-строка;
- фильтры по периоду, категории, действию и автору.

Одно пользовательское действие отображается одним событием. Массовое изменение категории не раскладывается на десятки событий.

Каждое событие должно отвечать на вопросы:

- когда;
- где;
- кто;
- что изменил.

## 8. Frontend data flow

### 8.1 Единичный товар

1. Пользователь меняет `Switch`.
2. Контрол временно блокируется.
3. Frontend вызывает существующий `save_active` с одним товаром.
4. После успешного ответа frontend заменяет локальное значение авторитетным состоянием сервера.
5. Если текущий endpoint не возвращает полное состояние, frontend сразу повторяет `get_items`.
6. При ошибке остаётся предыдущее серверное состояние и показывается `Повторить`.

Оптимистическое локальное мутирование `cats/items` не является источником истины.

### 8.2 Категория

1. Frontend отправляет intent `is_active: 0 | 1`.
2. Сервер определяет актуальный состав категории.
3. Сервер атомарно обновляет только отличающиеся товары.
4. Сервер возвращает авторитетное состояние категории.
5. Frontend заменяет данные категории ответом сервера либо повторяет `get_items`.

При переключении точки незавершённый ответ предыдущей точки не должен перезаписать новую выборку. Нужны cancellation/request identity или проверка актуального `point_id`.

## 9. API

### 9.1 `get_items`

Request:

```json
{
  "point_id": 7
}
```

Требования к response:

- каждый товар содержит известные поля `item_id`, `name`, `category_id`, `is_active`;
- `is_active` всегда нормализован в `0 | 1`;
- frontend не обрабатывает `null` как отдельное состояние.

### 9.2 `save_active`

Endpoint сохраняется для единичного товара. Текущий wrapper с массивом можно сохранить, но frontend отправляет один элемент:

```json
{
  "point_id": 7,
  "items": [
    {
      "item_id": 1428,
      "is_active": 1
    }
  ]
}
```

Response обязан вернуть подтверждённое сервером состояние изменённого товара или достаточно данных для немедленной замены категории. Если это несовместимо с текущим envelope, обязательным fallback становится `get_items`.

### 9.3 `save_category_active`

Новый request:

```json
{
  "point_id": 7,
  "category_id": 23,
  "is_active": 0
}
```

Обязательные свойства операции:

- проверка доступа к точке и категории;
- `is_active` допускает только `0 | 1`;
- состав категории определяется сервером во время операции;
- изменение и история выполняются в одной DB-транзакции;
- повторный intent к уже достигнутому состоянию не создаёт detail-записи для неизменённых товаров;
- response содержит `changed_count` и авторитетное состояние категории либо полный обновлённый список её товаров.

Рекомендуемый semantic response без привязки к конкретному API-envelope проекта:

```json
{
  "point_id": 7,
  "category_id": 23,
  "requested_is_active": 0,
  "changed_count": 5,
  "category": {
    "id": 23,
    "name": "Суши и роллы",
    "open_count": 0,
    "total_count": 12,
    "state": "closed",
    "items": [
      {
        "item_id": 1428,
        "name": "Филадельфия классик",
        "is_active": 0
      }
    ]
  }
}
```

### 9.4 `get_history`

Новый endpoint поддерживает pagination и фильтры:

- `point_id`;
- `date_from`, `date_to`;
- `category_id`;
- `event_type`;
- `actor_id`;
- `page`, `per_page`.

Pagination envelope следует существующему стандарту API проекта. Каждая строка данных нормализуется под текущий `HistoryLog`:

```json
{
  "id": 9182,
  "created_at": "2026-07-29T14:32:10+04:00",
  "actor_name": "Мария Иванова",
  "event_type": "category_closed",
  "diff_json": "{\"items\":[]}",
  "meta_json": "{\"point_id\":7,\"category_id\":23,\"changed_count\":5,\"legacy\":false}"
}
```

Предлагаемый enum:

- `item_opened`;
- `item_closed`;
- `category_opened`;
- `category_closed`;
- `legacy`.

## 10. Хранение истории

Логическая модель:

- event/header — одно пользовательское действие;
- event details — только реально изменённые товары.

Header хранит:

- автора;
- точку;
- время;
- `event_type`;
- запрошенное итоговое состояние;
- `changed_count`;
- snapshot названия категории;
- признак `legacy`.

Detail хранит:

- `item_id`;
- `old_is_active`;
- `new_is_active`;
- snapshot названия товара;
- `category_id`;
- snapshot названия категории.

`diff_json`:

```json
{
  "items": [
    {
      "item_id": 1428,
      "item_name": "Филадельфия классик",
      "category_id": 23,
      "category_name": "Суши и роллы",
      "old_is_active": 1,
      "new_is_active": 0
    }
  ]
}
```

`meta_json`:

```json
{
  "point_id": 7,
  "point_name": "Центр",
  "category_id": 23,
  "category_name": "Суши и роллы",
  "requested_is_active": 0,
  "changed_count": 5,
  "total_count": 12,
  "legacy": false
}
```

## 11. Транзакция массового изменения

Внутри одной DB-транзакции:

1. Получить и при необходимости заблокировать актуальные товары категории для точки.
2. Нормализовать текущий `is_active`.
3. Выбрать только товары, где `current !== requested`.
4. Создать один event/header.
5. Создать details только для выбранных товаров.
6. Обновить выбранные товары.
7. Commit.
8. Вернуть авторитетное состояние категории.

Если `changed_count = 0`, backend должен использовать единое правило: либо не создавать событие, либо создавать явно помеченное `no_change`. Для оперативного журнала рекомендуется не создавать событие.

## 12. Legacy

- Старые записи не переписываются.
- Недостоверный backfill запрещён.
- Если нельзя достоверно определить автора, точку, категорию или diff, запись получает `legacy: true`.
- UI показывает, какие сведения отсутствуют.
- Восстановление состояния из произвольной старой записи не добавляется.

## 13. Ошибки и конкуренция

- Состав категории, изменившийся после загрузки, обрабатывается по актуальному серверному составу.
- Параллельное изменение другим пользователем разрешается серверным порядком транзакций; frontend после ответа показывает фактический результат.
- API error не оставляет ложное локальное состояние.
- Повторное нажатие блокируется до завершения запроса.
- Переключение точки изолирует запросы по `point_id`.
- Если изменённых товаров нет, история не содержит пустой misleading diff.

## 14. Accessibility

- `Switch` всегда имеет видимую текстовую подпись.
- Mixed-state используется только как агрегированный статус.
- Для `Открыть все` / `Закрыть все` используются явные действия.
- Все интерактивные элементы доступны с клавиатуры.
- Фокус видим и не обозначается только цветом.
- Touch target — не меньше `44 × 44 px`.
- Статусы содержат текст, цвет служит дополнительным сигналом.

## 15. Проверка

- 360, 390, 430 px;

- полностью open, closed, mixed;
- один товар;
- единичное изменение;

- массовое закрытие и отмена;
- состав категории изменился между чтением и записью;
- API error и retry;
- повторное нажатие;
- смена точки;
- параллельное изменение;

- отсутствие неизменённых товаров в diff;
- фильтрация истории;
- keyboard и focus;
- доступные имена контролов;
- touch target.
