# План фронтенда: восстановление пароля Chef

## Предусловие

До доработки UI нужен утверждённый бизнес-контракт Telegram. Telegram Gateway i-Dgtl для OTP и обычный Telegram-бот, которому пользователь заранее передал номер, — разные модели доставки. Выбирается один вариант, после чего ему синхронно соответствуют backend-конфигурация, API-контракт и тексты интерфейса. Клиент не делает fallback между каналами.

## Последовательность работ

1. Не менять существующий вход, токены и API-транспорт до покрытия поведения backend: request/queue lifecycle, нераскрытие существования аккаунта, погашение кода после окончательной ошибки доставки и отсутствие fallback.
2. После этого оформить восстановление как явный state machine: номер и канал → CAPTCHA → ожидание кода → новый пароль → успешный вход либо управляемая ошибка. Канал передаётся явно в локальный Laravel API.
3. Изолировать транспорт в одном клиентском слое; исключить `api_new` и любые production URL. Ответ API остаётся нейтральным: UI не утверждает, что номер существует или Telegram доступен.
4. Добавить тесты переходов состояния, payload, cooldown и ошибок. Локальный test setup обязан включать явную test-конфигурацию SmartCaptcha или её детерминированную подмену.
5. Только после стабилизации поведения отдельно согласовать тексты и внешний вид. Scope — только Chef.

## Проверка

- Docker-first: локальный backend, локальная БД/очередь и поддельный HTTP-провайдер; без production и без реальных ключей.
- Для backend должны быть проверены реальные controller/request и queue lifecycle, провайдерные payload/ответы и отсутствие fallback.
- Живой smoke разрешён лишь после локальной настройки credentials/config и явного уведомления оператора: максимум по одной контролируемой отправке на SMS, Telegram и voice. В артефактах не указывать номер телефона, токены, пароли или другие секреты.
